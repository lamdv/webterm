# webterm desktop client

A Tauri client for remote webterm servers. It stores server profiles and, when
you connect, navigates its single window to that server's own web client — so
the app and the browser show exactly the same UI, and the session cookie and
WebSocket stay first-party.

This app does **not** run a server. `localhost` is simply one more profile.

## Layout

```
Cargo.toml              cargo workspace (two members)
rust-toolchain.toml     pins stable + rustfmt + clippy
crates/webterm-client/  portable logic: profiles, persistence, auth (no Tauri)
src-tauri/              the Tauri shell: windows, IPC, plugins
frontend/               the picker page (plain HTML/CSS/JS, no build step)
tutorial/               read this to learn the codebase and Rust
```

The split matters: anything testable without a window goes in
`crates/webterm-client`, which is what will let the same code compile for iPad
and Android later.

## Build

Prerequisites: `rustup`, the Tauri CLI, and the platform webview libraries
(Linux: `webkit2gtk-4.1`). See [tutorial/00-orientation.md](tutorial/00-orientation.md)
for the exact commands.

```bash
cargo test -p webterm-client   # fast: no window, no Tauri
cargo tauri dev                # run the app
cargo tauri build              # produce bundles
```

### Bundles

`cargo tauri build` writes the host platform's installers under
`target/release/bundle/`:

| Platform | Formats |
| --- | --- |
| Linux | `.deb`, `.rpm`, AppImage |
| macOS | `.app`, `.dmg` |
| Windows | `.msi`, NSIS `.exe` |

Only the host's formats are built locally; the CI matrix
(`.github/workflows/desktop-release.yml`) builds all of them and attaches the
artifacts on a `desktop-v*` tag. No distribution packaging tools are needed:
Tauri's bundler writes the `.deb`/`.rpm` itself and fetches `linuxdeploy` and
the AppImage runtime on first use. The Linux packages declare
`libwebkit2gtk-4.1-0` and `libgtk-3-0` as dependencies.

## Why the terminal UI is not in this repository

When you connect, the window navigates to the server's origin and loads the
server's `index.html` / `app.js` / `style.css`. Keeping the webview on the
server origin (rather than building our own terminal UI) is deliberate: it keeps
the session cookie and the WebSocket first-party and same-origin, which is what
makes OAuth2 proxies such as oauth2-proxy work without any server-side change.

The picker therefore cannot share a stylesheet with the server (different
origin, no CORS), so `frontend/picker.css` carries its own copy of the palette,
intentionally matching `webterm/static/style.css`. If you change one palette,
change the other.

## Security

- `capabilities/default.json` grants IPC to the `main` window, and it has no
  `remote` scope, so it applies only while that window is on the picker's local
  origin. Once the window navigates to a server it is a remote origin and every
  command is denied. This is enforced by the app ACL manifest declared in
  `build.rs` (`permissions/autogenerated/`), not just by the comment in the
  capability.
- `withGlobalTauri` is off, so there is no ambient `window.__TAURI__`. The
  picker reaches Rust through `frontend/ipc.js`, a one-function wrapper over the
  `window.__TAURI_INTERNALS__.invoke` bridge that the official API also uses.
- A server page therefore has the same (lack of) privileges a remote page has
  in any browser; the only way back to the picker is the native **Servers**
  menu, which runs in Rust.

## Profiles

Saved servers live in the per-app config directory
(`app_config_dir()/servers.json`, e.g. `~/.config/dev.webterm.desktop/` on
Linux). The file is written atomically and chmodded to `0o600` because a token
profile stores its secret there. Profiles can be added, edited and removed from
the picker; an edit keeps the profile's id.

## Authentication

- **Open** profiles navigate straight to the server.
- **Token** profiles navigate once to `/?bootstrap=<token>`; the server trades
  the secret for an `HttpOnly`, `SameSite=Strict` cookie and redirects to `/`,
  so the WebSocket authenticates with the cookie rather than a token in its URL.
- **Browser login** profiles send no credential and let an identity-aware proxy
  (oauth2-proxy, Authelia) run its own login in the window. This is the
  least-tested path; see [Roadmap](#roadmap).

The URL-building rule lives in `crates/webterm-client/src/connect.rs` and is
unit tested there.

## Server status

Each row is probed against the server's unauthenticated
`/.well-known/webterm.json` document using the `reqwest` client re-exported by
`tauri-plugin-http`. The status pill shows `v<version>` when the server is
reachable and compatible, `needs protocol N` when it is not, `no discovery`
when it answers but has no discovery document (an older server, or
`--no-discovery`), and `offline` only when the connection itself fails. Hover
the pill for the reason, or use the header's **Refresh** button. The auth pill
next to it shows which credential the profile will use. The document shape and
the discovery URL rule live in `crates/webterm-client/src/discovery.rs`.

## Menu and shortcuts

A native menu (`src-tauri/src/menu.rs`) provides **Servers**
(Cmd/Ctrl+Shift+S, back to the picker), **Reload Window** (Cmd/Ctrl+R), plus
predefined Quit, Minimize, Fullscreen and Close Window items. It is native so it
also appears while the window is showing a remote server page. Copy/Paste items
are deliberately absent: their default Ctrl+C / Ctrl+V accelerators would
swallow the terminal's SIGINT and paste keys.

There is no tray icon: the app has one window, and closing it quits.

## Window state

`tauri-plugin-window-state` remembers the window's size, position, maximized and
fullscreen state in `app_config_dir()/.window-state.json`. There is a single
window, so the picker and every server share one geometry rather than each
server keeping its own.

## Layout

The picker's sidebar (the add/edit form) is resizable with the same bounds as
the terminal's session switcher (150–640px, default 220px) and remembers its
width. On connect that width rides in the URL (`?sidebar=<px>`), so the server
view's sidebar lines up with the picker's. A narrow terminal view collapses its
sidebar regardless, collapses it again when a shell is chosen, and leaves the
expand button in reach — see `docs/frontend.md`.

## Roadmap

- [x] **oauth2-proxy integration test (automated half).**
  `desktop/scripts/oauth2-proxy-test/run.sh` starts oauth2-proxy in front of a
  local webterm with a stdlib mock OIDC provider and asserts: an unauthenticated
  request redirects to the IdP, the sign-in page serves, the callback sets the
  `_oauth2_proxy` cookie, the authenticated UI reaches webterm, and `/ws` is 302
  without the cookie and 101 with it. All pass (curl; no webview involved).
- [ ] **Watch the webview do that login.** The script cannot drive the Tauri
  webview, so this half is manual: add a `browser` profile pointing at an
  oauth2-proxy URL, click Connect, and confirm the provider's login page renders
  and the terminal loads after sign-in. The main risk is IdPs that refuse
  embedded user-agents (Google), which no local IdP will reproduce. Follow-ups
  to decide afterwards: a **Sign in again / Clear session** menu action, a
  "login required" probe state (the discovery probe is unauthenticated, so the
  pill stays green while logged out), and OIDC popup handling.
- **Not planned: proxy plus webterm `--token`.** The supported shape is
  oauth2-proxy alone (no `--token`), with webterm bound to `127.0.0.1` and the
  proxy gating every route including `/ws`. oauth2-proxy's own `--upstream` mode
  cannot inject a static `Authorization` header, so combining it with `--token`
  would need an nginx/Caddy `forward_auth` in front; that is deliberately out of
  scope for now.
- [x] **Package the app.** `cargo tauri build` bundles deb/rpm/AppImage on
  Linux (verified: 6.6/6.6/112 MiB, correct `.desktop`, categories and
  dependencies); the CI matrix builds macOS `.app`/`.dmg` and Windows
  `.msi`/NSIS and publishes them on a tag. macOS signing/notarization is still
  outstanding for distribution.
